# MRA V1.1 一次性黏性处方验收记录

> 验收日期：2026-08-23（Asia/Shanghai）
>
> 当前结论：全局 fail-open 提醒入口已经升级为“每个 Codex 对话/任务只处方一次”。CLI、app-server 与直接 Hook 场景已验证；下一条真实桌面端新任务仍是最终人机界面验收点。不得把本结论改写为程序级硬锁、零漏触发或自动模型切换。

## 一、问题与根因

归档不是先前持续漏处方的根因，也不是后来重复弹卡的根因。

最初漏处方有一个直接原因：V0.1 的历史状态明确为 `global_gate_enabled: false`，当时只有 Skill 描述匹配，没有全局 `AGENTS.md` 强制入口，也没有 `UserPromptSubmit` Hook。不主动提到选模型的新任务，可能根本不会触发路由 Skill。

第一版全局入口补上了漏触发，但把连续执行、阶段变化、风险变化和归档恢复都当成重新检查条件。该设计会让同一任务反复出现路由卡，不符合用户“项目方向在建立初期只决定一次”的要求。

V1.1 因此把处方作用域固定为一个 Codex 对话/任务：首次实质请求处方一次；确认后，后续阶段、范围、风险、动作权限、交付对象变化及归档恢复全部静默沿用。只有用户明确要求改选，或已选模型/档位经当前运行时核验不可用，才允许重新路由。

用户在 V0.1 原指标尚未达到时明确选择“优先保证质量”并授权进入全局门。V0.1 的最终数据为 5 个自然日、3 个有效路由决策、0 个闭环任务、接受推荐率 66.7%、3 个实际配置待核实项、0 个效率改善信号。这是用户显式覆盖原晋级门槛，不是 V0.1 指标通过。

## 二、当前策略

1. 普通寒暄、简单解释和微小追问不消耗处方机会。
2. 每个新 Codex 对话/任务的首个非闲聊、实质请求，在实质工作前只生成一张路由卡并等待确认。
3. 首次选型按该对话或项目可预见完整生命周期中的最高复杂度和最高风险下限进行，确保固定路线覆盖后续阶段。
4. 路由卡尚待确认时，后续消息只指向已有卡片，不生成第二张。
5. 用户确认后，同一对话内的计划、执行、验证、部署、高风险措辞、第二项工作和归档恢复都静默沿用。
6. 只有用户明确要求重新选型、改变额度偏好，或运行时核验已选配置不可用时，才生成一张替换卡；替换卡待确认期间同样不重复。
7. 模型确认只决定模型与推理档位，不替代发布、付款、删除、部署、隐私、安全或外部行动门禁。

## 五、安全、隐私与边界

- Hook 使用 `continue: true`；异常时告警并放行用户消息，因此不是不可绕过的强制锁；
- `route_selection_observed` 只表示观察到选择短语，不等于宿主已经切换到推荐模型与档位；
- 当前作用域是一个 Codex 对话/任务。新建独立对话会再询问一次，不跨对话自动继承；
- 启发式语义判断仍可能误报或漏报，不能宣称所有宿主、所有表达永不漏触发；
- 为避免旧任务被遗忘，状态和事件日志目前都不做有损淘汰，会随会话数线性增长；长期方案应迁移到精确、无损的持久账本，不能用固定容量或 TTL 换回重复弹卡；
- 运行日志只保存元数据和提示词 SHA-256，不保存原始提示词；哈希不是匿名化承诺；
- 发布、付款、删除、部署、安全等单独门禁始终有效，不能因模型已确认而自动放行；
- 桌面 UI 和运行时不可用异常仍有待后续真实场景验证。

## 七、验收结论

可以确认的是：已知的“只靠隐式 Skill 导致漏处方”路径已补上；旧版“连续执行、阶段变化、高风险变化和归档恢复反复弹卡”路径已从规则、Hook 状态、升级管理器和回归测试中移除，并在真实 CLI 的确认、阶段变化和归档恢复链路上通过验证。

不能确认的是：所有宿主绝不漏触发、模型已自动切换、高风险工具被程序硬阻断，或桌面端完整卡片已经验收。下一条真实桌面新任务应只出现一张卡；确认后该任务后续不再出现卡，除非用户明确要求改选或运行时证明确实不可用。
