# 全局模型路由门禁契约

> 契约版本：`global-gate/1.0`
>
> 本文定义统一任务入口如何判断“新建路由、沿用确认、恢复或阻断”。它不改变 `scripts/route_model.py` 的输入输出、路由卡格式或 V0.1 试运行事件格式。

## 1. 目标与强制边界

统一入口的目标是让每次实质任务先得到一个可检查的门禁状态，再决定是否展示路由卡。**每轮评估**不等于**每轮弹卡**；同阶段已有有效确认时应沿用，避免重复打断。

本 Skill 只能规定合规入口与主执行者应怎样工作，不能单独证明 Codex 桌面端、CLI 或其他宿主已经安装并执行首轮 Hook，也不能替用户切换模型。V1 Hook 是 fail-open 的消息传输与提醒层，不是 `PreToolUse` 或等价的程序级执行硬锁。没有宿主调用记录、门禁凭证和相应 E2E 证据时，只能报告“全局门未验证”，不得宣称已经绝对强制、零漏触发、程序已阻断高风险工具或已切换到所选模型。

统一入口允许在确认前读取完成分类所必需的最小元数据，例如用户当前请求、项目标识、工作目录、既有确认凭证、模型目录版本和上游门禁状态；不得借“分类”之名提前开始代码修改、长链研究、内容生产、外部调用或现实动作。

## 2. 术语

- **任务**：具有独立目标、交付物或验收条件的一段工作，不等同于整个项目，也不等同于单条消息。
- **阶段**：`investigate`、`plan`、`execute`、`verify`、`deploy` 之一。
- **实质执行**：会产出任务交付物、写本地文件、调用外部系统、进行长链调查或改变现实状态的动作。为判定门禁而进行的最小只读检查不属于实质执行。
- **门禁评估**：判断是否需要新路由、能否沿用确认、是否应告警或阻断。
- **路由卡**：按 [路由卡格式](routing-card-schema.md) 展示的模型与档位建议。
- **确认凭证**：用户明确选择后，绑定当前任务、阶段和推荐结果的结构化记录。它不证明宿主已经完成模型切换。

## 3. 统一入口契约

合规入口应在实质执行前完成以下判定：

1. 取得当前任务文本、可用项目标识、阶段、动作范围、风险、交付对象、用户额度偏好，以及现有确认凭证；未知值保持未知，不用默认值伪造证据。
2. 先检查上游决策、内容、权限和安全门禁。上游已阻断时返回 `blocked-upstream`，不以更强模型绕过。
3. 计算当前任务指纹，校验现有确认凭证是否匹配且仍在有效期内。
4. 按正负触发规则得出门禁状态。需要新路由时再调用现有分类与 `scripts/route_model.py`；不需要时明确返回 `routing-not-required`，不能以无输出代替判断。
5. 路由卡展示后进入 `awaiting-user-confirmation`。用户明确确认前，不开始依赖该路由的实质执行。
6. 用户确认后生成确认凭证并进入 `routing-confirmed`。实际模型与档位只有宿主提供可核验证据时才记录为已切换。

完整门禁适配器应负责门禁状态与确认凭证；当前 V1 Hook 只负责 `inject / skip` 和故障告警。`scripts/route_model.py` 仍只接收 [路由策略](routing-policy.md) 定义的任务字段，并返回原有推荐 JSON。

宿主 Hook 的 `inject / skip` 只是“是否向本轮注入门禁提醒”的传输决定，不是本节定义的业务状态：`inject` 不等于一定要弹新卡，`skip` 也不证明用户已经确认。执行者仍须以当前任务指纹和确认凭证判断 `routing-not-required`、`awaiting-user-confirmation` 或其他最终状态。

## 4. 状态名与转换

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `routing-not-required` | 已完成评估；同阶段有效确认可沿用，或当前只是无需路由的轻量交互 | 回答当前轻量请求，或在原确认范围内继续 |
| `routing-required` | 命中正向触发，尚未形成卡片 | 完成分类、运行路由器并生成卡片 |
| `awaiting-user-confirmation` | 路由卡已展示，等待用户明确选择 | 解释卡片或回答确认相关问题；不做实质执行 |
| `routing-confirmed` | 用户已明确确认，且当前确认凭证有效 | 在凭证覆盖的任务与阶段内执行 |
| `routing-stale` | 原凭证因任务、阶段、风险、策略或目录变化失效 | 转为 `routing-required`，不得静默沿用 |
| `blocked-upstream` | 上游决策、内容、权限或安全门禁未通过 | 返回阻断原因和可补证据，不做路由替代 |
| `gate-warning` | 低或中风险任务的门禁基础设施失败，按 fail-open 规则告警 | 仅在第 9 节边界内继续，并保留未路由事实 |
| `blocked-awaiting-routing` | 高风险或用户明确要求确认的任务没有有效路由 | 主执行者只允许修复门禁、补信息或展示路由卡；V1 尚无程序级硬锁 |

正常路径为：

```text
routing-required → awaiting-user-confirmation → routing-confirmed
```

凭证失效路径为：

```text
routing-confirmed → routing-stale → routing-required
```

`routing-confirmed` 只证明用户选择，不得改写成“模型已切换”或“任务已完成”。

## 5. 正向触发

以下任一情况需要新路由卡：

| 条件 | `route_trigger` 兼容值 | 判定要点 |
|---|---|---|
| 新项目首次进入实质工作 | `new_project` | 问候、创建空任务或只讨论需求不算已进入实质工作 |
| 同一项目出现新的独立目标、交付物或验收条件 | `scope_change` | 任务目标变化，而不是措辞变化 |
| `investigate / plan / execute / verify / deploy` 发生变化 | `stage_change` | 尤其是从只读调查进入写入、验证或上线 |
| 动作范围由只读升级为本地写入或外部影响 | `scope_change` | 降级为更安全范围也可重新评估以节省额度 |
| 风险标记、错误代价或交付对象使风险下限变化 | `risk_change` | 公开发布、客户交付、付款、隐私、安全和不可逆动作优先 |
| 恢复重要工作，但原凭证缺失、未确认、失效或无法归属当前任务 | `resume_significant_work` | 单纯归档或取消归档不是触发条件 |
| 用户明确询问选模型、要求省额度/保质量或要求重新路由 | `user_requested` | 用户偏好变化也归入此项 |

判断用户当前**准备做什么**，不要只扫描孤立词语。新任务若只是普通事实回答、澄清或微小格式修改，可以评估为 `routing-not-required`；一旦将进入多步骤交付、写入、长链调查或外部动作，即视为实质工作。

## 6. 负向触发与去重

以下情况不得仅因出现模型、阶段或风险关键词而重复弹卡：

- 同一任务、同一阶段、同一动作范围和风险下限下的连续执行；
- 用户对当前路由卡的确认、改选或追问；确认消息只推进状态，不生成第二张卡；
- 普通状态询问、解释、澄清、错别字修正、纯格式微调或不改变验收条件的小改动；
- 仅发生归档、取消归档、窗口重开或任务列表位置变化；
- 引用、复盘或否定未来动作，例如“不要部署”“尚未进入发布”“这段只是在讨论付款风险”；
- 文档、测试夹具或历史记录中出现 `deploy`、`payment`、`public_release` 等词，但用户没有执行这些动作的当前意图。

否定语义优先于孤立关键词；明确的当前行动意图优先于背景描述。无法判断否定范围且可能改变风险下限时，只问一个关键问题，不要猜测后直接执行。

## 7. 任务指纹、阶段变化与确认凭证

任务指纹至少由以下稳定信息组成：项目标识或根目录、规范化任务目标、交付物或验收条件、`stage`、`action_scope`、`task_kind`、`risk_floor`、风险标记、交付对象和用户偏好。不得只用聊天标题、文件名或归档状态作为指纹。

以下变化使凭证失效：

- 进入新阶段或新的独立任务；
- 动作范围、风险下限、风险标记、交付对象或用户偏好变化；
- 上下文或工具负荷跨过会改变推荐结果的阈值；
- 路由器版本、路由策略或当前模型目录发生影响推荐的变化；
- 凭证无法证明对应当前任务，或用户尚未明确确认。

确认凭证至少包含：

| 字段 | 要求 |
|---|---|
| `schema_version` | 固定为本契约版本 |
| `task_id` | 同一阶段的路由决策与结果共用；阶段变化创建新值 |
| `thread_id` | 宿主可提供时记录；不可用时为 `null` 并保留限制说明 |
| `task_fingerprint` | 绑定当前任务与阶段 |
| `route_trigger` | 使用第 5 节兼容枚举 |
| `stage`、`action_scope`、`task_kind`、`risk_floor`、`risk_flags`、`preference` | 复制路由时的原始分类，不从推荐结果反推 |
| `router_version` | 与路由器输出一致 |
| `catalog_fingerprint`、`policy_fingerprint` | 用于识别目录或策略是否过期 |
| `recommended_model`、`recommended_effort` | 路由卡推荐值 |
| `card_digest` | 绑定用户实际看到的结构化推荐，不依赖 Markdown 空白 |
| `user_choice` | `accept_recommended`、`prefer_quota`、`prefer_quality` 或 `custom` |
| `selected_model`、`selected_effort` | 用户明确选择的配置 |
| `confirmed_at` | 带时区的 ISO 8601 时间 |
| `runtime_switch_verified` | 默认 `false`；只有宿主证据才能设为 `true` |

确认必须来自用户对当前卡片的明确选择，不能从用户继续聊天、Agent 自报或“看起来接受”推断。卡片、确认凭证、实际模型运行和任务结果是四种不同证据。

上述字段是确认凭证的验收合同，不自动证明 V1 Hook 已实现持久化。在确认凭证的写入、读取、过期和归档恢复尚未完成真实 E2E 前，V1 只能注入重新评估提醒；不得声称已自动恢复或稳定沿用历史确认。

若 V0.1 试运行处于激活状态，确认凭证形成后再按 [试运行协议](trial-protocol.md) 追加 `route_decision`；阶段变化使用新的 `task_id`。本契约不增加或改写试运行事件字段。

## 8. 归档与恢复

归档状态只影响任务可见性，不应删除、确认或伪造路由凭证。恢复后的首条实质请求按以下顺序处理：

1. 查找与当前任务指纹、阶段、策略和目录版本完全匹配的 `routing-confirmed` 凭证；
2. 匹配成功则返回 `routing-not-required`，注明“恢复并沿用已有确认”，不重复弹卡；
3. 凭证缺失、未确认、失效或任务目标已变化时返回 `routing-stale`，再以 `resume_significant_work` 重新路由；
4. 宿主无法提供稳定任务或线程标识时，不得声称恢复成功。高风险任务按 fail-closed 处理；低或中风险任务重新评估或进入显式告警。

因此，“曾被归档”本身既不是漏触发原因，也不是重复触发理由；有效凭证和当前任务指纹才是依据。

如果 V1 Hook 只能识别“恢复”语义并重新注入门禁提醒，而没有确认凭证持久化证据，应如实报告“已重新检查，自动恢复确认未验证”，再由主执行者决定是否需要新卡。

## 9. 失败策略

门禁脚本、模型目录核验、确认凭证读取或持久化失败时，必须保留具体错误，不得静默当作 `routing-not-required`。

V1 的宿主 Hook 使用 `continue: true` 保证用户消息不会因门禁故障而丢失，并通过系统消息显式告警。这里的 fail-open 只允许会话继续，不代表已经授权实质执行。

当前所谓“高风险 fail-closed”是全局指令和主执行者行为门：执行者收到 `gate-warning` 后，仍须按下列风险边界决定继续或返回阻断。除非以后实现 `PreToolUse` 或等价硬锁并完成真实 E2E 验证，否则不得把它描述为 Hook 已经从程序层阻止工具调用。

### 高风险实质执行行为门（非程序级硬锁）

满足任一条件时，主执行者应返回 `blocked-awaiting-routing`：

- `risk_floor` 为 `high` 或 `critical`；
- `stage == deploy` 或 `action_scope == external_effect`；
- 命中生产、公开发布、付款、法律、安全、隐私、客户交付或不可逆风险；
- 用户明确要求“先给路由卡并等我确认”；
- 无法判定的未知项可能把任务提升到上述范围。

只允许修复门禁、补齐关键事实或重新展示路由卡，不得以当前默认模型继续实质执行。

### 低、中风险告警后继续

仅当任务可确定为 `low` 或 `medium`、没有外部影响和上述风险标记、用户也未要求先确认时，才可进入 `gate-warning` 并继续。必须同时：

- 明确告知“本轮未形成有效路由凭证，沿用当前配置不代表最优路由”；
- 记录失败原因和未验证字段；
- 不写入接受推荐的试运行证据，不宣称 Skill 已正常运行；
- 后续风险或范围升级时立即转为 fail-closed。

Fail-open 是基础设施故障下的有限降级，不是日常跳过路由的捷径。

## 10. 兼容性与验收不变量

- `scripts/route_model.py` 的输入字段和输出 JSON 保持不变；门禁字段由统一入口管理。
- 用户可见卡片继续使用现有一屏格式和三种确认选项。
- 用户确认不等于宿主切换模型；无法观察实际配置时保持未知。
- 试运行仍只在用户明确确认后记录 `route_decision`，并沿用现有 `task_outcome` 规则。
- 上游门禁、真实测试、用户验收和外部完成证据均不能被模型路由替代。

触发契约变更至少应覆盖以下成对回归：

1. 新项目/新阶段/风险升级会触发，同阶段普通追问不会触发；
2. 明确准备部署会触发，“不要部署”或引用部署文档不会误触发；
3. 卡片确认只生成一次凭证，不会再弹一张卡；
4. 归档恢复且凭证有效会沿用，凭证缺失或过期会重新路由；
5. 高风险门禁故障时主执行者会返回行为阻断，低或中风险降级会显式告警；
6. 只有卡片没有用户确认时，不得进入 `routing-confirmed`；
7. 只有用户确认没有宿主证据时，不得写 `runtime_switch_verified=true`。

只有宿主入口、状态持久化、正反回归和真实任务闭环都已有证据时，才能描述为“已接入 V1 fail-open 提醒门禁”。只有另行实现程序级执行硬锁并通过真实 E2E 后，才能声称高风险动作被程序阻断；任何阶段都不得夸大为所有环境绝不漏触发。
