# 全局模型路由门禁契约

> 契约版本：`global-gate/1.2`
>
> 本文定义“一次处方、全程沿用”的模型路由入口。它不改变 `scripts/route_model.py` 的输入输出，也不授予任何高风险动作权限。

## 1. 目标与强制边界

每个新的 Codex 对话或任务在首次进入实质工作前，只显示一张模型路由卡。首次推荐必须按该对话可预见完整生命周期的最高复杂度与风险下限选型，而不是只按开场时的轻量调查、讨论或规划选型。

经 Codex 宿主 transcript 元数据核验的独立 cron 运行是明确例外：模型与推理档位在创建或更新自动化时固定，每次运行新建的会话不再显示模型路由卡。heartbeat 复用既有目标任务，沿用该任务已经确认的黏性路线；目标任务尚未确认时只保留原有一张卡，确认一次后未来唤醒不再询问。

用户确认后，该配置成为本对话或任务完整生命周期的默认处方。后续调查、规划、执行、验证、部署、风险变化、材料变化和归档恢复都静默沿用，不自动再次询问。

只有以下两类情况允许重新路由：

1. 用户明确要求重选模型或明确改变“平衡 / 节省额度 / 保证质量”偏好；
2. 当前运行时提供可核验证据，证明已选模型不可用或已经退役。

模型目录刷新、材料增减、阶段变化、风险变化、交付对象变化或上下文变长，单独出现时都不是重新弹卡的理由。实质上另起新项目时，应从新的 Codex 对话或任务入口获得新处方。

模型路由只分配计算资源，不批准付款、签约、部署、发布、删除、客户交付、隐私处理、外部消息或其他现实动作。所有业务、安全、权限、内容和验收门禁始终独立有效。

## 2. 术语

- **处方作用域**：一个 Codex 对话或任务。该作用域内只允许一张首次卡；命中允许的例外时可以用替代卡取代已确认的旧处方，但任一时刻只能有一张待确认卡。
- **可预见完整生命周期**：根据当前目标、交付物和已知计划，预计会经历的调查、规划、执行、验证、部署和交付范围。
- **实质工作**：会形成交付物、进行长链调查、写文件、调用工具、影响外部系统或改变现实状态的工作。普通寒暄和简单解释不属于实质工作。
- **路由卡**：按 [路由卡格式](routing-card-schema.md) 展示的模型和推理档位建议。
- **确认**：用户对当前唯一卡片明确选择“按推荐执行 / 优先节省额度 / 优先保证质量”或明确指定其他配置。
- **运行时可用性证据**：当前 Codex 宿主的可见模型清单、明确不可用错误、退役信息或等价的当前运行时证据；仅凭旧文档或猜测不算。
- **经核验的独立 cron 运行**：Hook 从 Codex 受信目录中的当前 transcript 首条 `session_meta` 核验到 `thread_source=automation`，同时核对文件所有者、路径、文件名和会话标识。严格 cron 信封与本机 `ACTIVE` 配置只用于识别哪一轮是自动触发，不能单独创建自动化豁免。用户正文中出现“自动化”“每日任务”或复制真实信封都不构成该证据。
- **heartbeat 目标任务**：heartbeat 不凭信封创建豁免；它复用 `target_thread_id` 对应任务已经存在的一次性路由状态。目标任务已确认则静默沿用，尚未确认则继续等待同一张卡。

## 3. 统一入口契约

合规入口在首次实质工作前依次完成：

1. 先判断当前输入是否是经受信 transcript 核验的独立 cron 运行。命中自动触发轮时返回 `routing-not-required / scheduled_automation`，不显示卡片、不等待确认，继续执行自动化业务流程；该运行任务里的普通人工跟进只沿用自动化线程配置，不冒充新的定时触发。
2. 非自动化输入再判断当前消息是否属于一个新 Codex 对话或任务的首次实质工作。
3. 检查本处方作用域是否已经展示过卡片、是否仍在等待确认，或是否已有明确确认。
4. 没有卡片时，读取当前模型目录和路由策略，按可预见完整生命周期的最高复杂度、上下文、工具负荷、错误代价与风险下限生成一张卡。
5. 卡片已展示但尚未确认时，继续等待或解释原卡；不得重新计算、改写或展示第二张卡。
6. 已确认时，返回 `routing-not-required` 并静默沿用。阶段变化、风险变化、部署和归档恢复不改变此结果。
7. 只有用户明确要求重选或改变额度偏好，或运行时证实所选模型不可用或退役时，才使原选择失效并生成一张替代卡。
8. 无论路由状态如何，都单独检查当前动作所需的业务授权、安全门、内容门、发布门和验收门。

用户确认只证明选择了处方，不证明宿主已经切换模型，不证明任务完成，也不构成任何现实动作授权。

## 4. 状态与转换

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `routing-required` | 新处方作用域首次进入实质工作，尚未展示卡片 | 完成首次分类并展示一张卡 |
| `awaiting-user-confirmation` | 唯一卡片已展示，尚未得到明确确认 | 等待、解释或澄清原卡；不得展示第二张或开始依赖该路由的实质工作 |
| `routing-confirmed` | 用户已明确选择当前处方 | 在其他门禁允许的范围内执行 |
| `routing-not-required` | 已确认且本轮应静默沿用、只是轻量交互、经核验的独立 cron 运行，或 heartbeat 目标任务已有确认 | 不显示路由卡，继续当前交互或自动化业务流程 |
| `routing-stale` | 用户明确要求重选/改变额度偏好，或运行时证实所选模型不可用/退役 | 生成一张替代卡并等待确认 |
| `blocked-upstream` | 独立的权限、安全、内容、业务或验收门禁未通过 | 返回阻断原因；不得用更强模型绕过 |
| `gate-warning` | 一次性提醒 Hook 或路由基础设施发生故障 | 明确告警并保留实际路由未知；是否执行仍由独立风险门决定 |

首次正常路径：

```text
routing-required → awaiting-user-confirmation → routing-confirmed → routing-not-required
```

允许的例外重路由：

```text
routing-confirmed → routing-stale → awaiting-user-confirmation → routing-confirmed
```

不得把阶段变化、风险变化、部署或归档恢复接到 `routing-stale`。

## 5. 首次卡片的选型口径

首次分类必须覆盖当前对话可预见的完整生命周期。至少考虑：

- 最终交付物和验收标准，而不只考虑首条请求的措辞；
- 预计最高阶段，包括是否可能进入写入、验证、部署或公开交付；
- 预计最大的上下文、工具调用和多 Agent 负荷；
- 生命周期内最高错误代价和风险标记；
- 用户首次声明的额度偏好。

例如，一个从调研开始但明确会进入生产部署的任务，首次卡片就按部署生命周期的最高风险下限选型，不能先给低配卡再在部署前自动重问。

只有关键未知项会改变完整生命周期的最高下限时，才允许在展示首次卡片前问一个问题。卡片展示后，新材料不得触发第二张卡。

## 6. 不得自动重新路由的变化

用户确认后，下列变化全部静默沿用：

- `investigate / plan / execute / verify / deploy` 阶段变化；
- 从只读变为本地写入或外部影响；
- 风险标记、错误代价或交付对象变化；
- 上下文、文件、数据、工具和材料增减；
- 目标细化、验收补充和普通范围调整；
- 归档、取消归档、窗口重开或继续上次工作；
- 用户询问状态、解释原建议或进行微小修改。

这些变化可能触发独立的权限、安全、发布或验收门，但不能触发模型卡。

## 7. 允许的例外重路由

### 用户明确要求

只有用户清楚表达“重新选模型”“改成省额度”“改为质量优先”或等价意图时，才把原处方标为 `routing-stale`。模糊抱怨、普通追问或继续执行不能推断为重选请求。

### 模型不可用或退役

只有当前运行时证据证明已选模型不可用或退役时，才生成替代卡。模型目录有新版本、出现新模型、默认模型改变或价格信息变化，但原模型仍可用时，继续沿用，不主动重问。

替代卡仍须等待用户确认。替代卡尚未确认时，不得继续生成更多卡片。

## 8. 定时自动化、未确认、归档与新对话

- 经宿主 transcript 核验的独立 cron 自动化，每次自动触发都返回 `routing-not-required / scheduled_automation`。它不会因为每天生成新 session 而重新问卡；同一运行任务中的普通人工跟进标记为 `automation_thread_followup`，不注入“本次定时触发”的执行提示。
- cron 的模型与推理档位在自动化创建或更新时决定。改变自动化模型应通过自动化更新流程完成，不应在无人值守运行中临时询问。
- heartbeat 沿用目标任务的一次性路由状态。目标任务已经确认时未来唤醒静默沿用；尚未确认时继续等待原卡，用户确认一次后不再重复询问。heartbeat 信封不能单独写入确认或豁免状态。
- 自动化正文中的“质量优先”“模型”“切换”或“重新生成模型数据”等业务措辞不是人工重选。只有用户在自动化任务里的后续人工消息明确要求重选时，才允许进入 `routing-stale`。
- 定时自动化豁免只取消模型路由等待，不豁免权限、安全、发布、付款、删除、隐私、内容、客户交付或真实验收门。自动化遇到这些独立门禁时仍必须按原规则停止或降级。
- cron transcript 缺失、损坏、越界、会话标识不符或 `thread_source` 不是 `automation` 时，必须按普通新对话规则处理；严格信封与本机配置即使完整匹配也不能单独创建豁免。heartbeat 则只读取目标任务已有路由状态，不从信封推导确认。

- 原卡尚未确认时，任何后续消息都维持 `awaiting-user-confirmation`；可以解释原卡，但不能生成第二张。
- 同一任务归档后恢复，已有确认则静默沿用；尚未确认则继续等待原卡。
- 当前 Hook 不保存结构化确认凭证。能否跨宿主重启定位原卡与确认，取决于对话历史是否仍可用；没有证据时不得声称已经自动恢复确认。
- 新建独立 Codex 对话或任务时，视为新的处方作用域，在首次实质工作前重新显示一张卡。
- 同一对话中实质上另起完全独立的新项目，应建议使用新的 Codex 对话承载；在原对话内不得借此自动弹第二张卡。

## 9. 与高风险审批和安全门的边界

路由确认永远不替代以下门禁：

- 生产部署、服务重启、配置切换和数据迁移审批；
- 付款、采购、签约和其他财务授权；
- 公开发布、广告投放、客户交付和外部消息授权；
- 删除、覆盖、不可逆变更和恢复方案确认；
- 法律、隐私、安全、内容合规和知识产权审查；
- 真实测试、人工验收和外部完成证据。

即使处方已经确认，任何上述门禁未通过时仍返回 `blocked-upstream`。不得把“模型足够强”当成执行授权。

## 10. 当前 Hook 的真实能力

当前 V1.2 `UserPromptSubmit` Hook 是一次性提醒与自动化识别层：它应在人工新对话或任务首次实质请求时注入检查提示，此后不靠阶段、风险、部署或恢复语义重复注入；经 transcript 元数据核验的独立 cron 自动触发则记录 `scheduled_automation` 并跳过模型卡。heartbeat 依靠目标任务已经确认的黏性状态，不依靠信封旁路。

Hook 使用 `continue: true`，因此它是 fail-open 的消息层，不是 `PreToolUse` 或等价的程序级硬锁。它不保存用户确认凭证，不判断宿主是否真的切换模型，也不自动切换模型。Hook 的 `inject / skip` 只是传输结果，不等于 `routing-confirmed`。

Hook 或 Skill 故障时必须显式报告“全局门未验证”或“实际模型未知”。高风险动作是否停止仍由第 9 节的独立门禁决定，不能宣称 Hook 已从程序层阻断工具。

`thread_source=automation` 是当前宿主观测到的元数据，不是 Hook 的公开顶层输入字段。实现必须校验 transcript 路径、所有者和会话标识；不得仅凭提示词关键词、cron/heartbeat 信封或本机自动化配置形成可绕过的豁免。

## 11. 兼容性与验收不变量

- `scripts/route_model.py` 的输入字段和输出 JSON 保持不变。
- 用户可见首次卡片继续使用一屏格式和三种确认选项。
- 一个处方作用域最多显示一张首次卡；原卡未确认时不显示第二张。
- 确认后阶段、风险、部署和归档恢复均不自动弹卡。
- 经宿主核验的独立 cron 连续多日运行不显示模型卡；已确认目标任务上的 heartbeat 连续多日唤醒也不再显示模型卡。自动化任务内的后续人工明确重选仍只允许一张替代卡。
- 伪造自动化文字、无效 transcript、会话标识不符或非 automation 元数据不得绕过普通新任务路由。
- 只有用户明确重选/改变额度偏好，或运行时证明模型不可用/退役时，才允许一张替代卡。
- 用户确认不等于模型已切换，更不等于高风险动作已获授权。
- V0.1 试运行只记录实际展示并得到明确确认的路由卡；静默沿用不伪造新确认。

只有宿主入口、真实新对话和真实定时运行验证都已有证据时，才能描述为“已接入一次性 fail-open 提醒与自动化免询问门”。没有程序级硬锁和运行时切换证据时，不得声称绝不漏触发、已阻断高风险工具或已自动切换模型。
