# 模型路由顾问

为一个 Codex 对话或任务选择覆盖其可预见完整生命周期的最小充分算力，并把推荐、理由、额度级别和例外重路由条件交给用户确认。

## 入口与触发

- 当本 Skill 被统一任务入口调用，或需要判断首次路由、沿用、归档恢复及例外重路由时，先完整读取 [全局门禁触发契约](references/global-gate-contract.md)，并在实质执行前给出其中定义的门禁状态。
- 一个 Codex 对话或任务是一条处方作用域。首次实质工作只显示一张卡；用户确认后，规划、执行、验证、部署、风险变化、材料变化和归档恢复都静默沿用，不自动重问。
- 只有用户明确要求重选、明确改变额度偏好，或已选模型被当前运行时证明确实不可用或已退役时，才生成替代卡。原卡尚未确认时继续等待原卡，不得生成第二张。
- 本 Skill 不能保证宿主首轮调用，也不能自动切换模型。当前 V1 Hook 只做一次性 fail-open 提醒，不是确认凭证、程序级硬锁或模型切换器；没有宿主或运行时证据时，明确写“全局门未验证”或“实际模型未知”。

## 执行流程

1. 先确认上游门禁状态。模型路由只分配计算资源，不批准付款、发布、部署、删除、客户交付或其他高风险动作；相关权限、安全和业务审批始终独立生效。上游已阻断时返回 `blocked-upstream`，不要用更强模型绕过。
2. 首次生成卡片或命中允许的例外重路由时，完整读取 [当前模型目录](references/current-model-catalog.md) 和 [路由策略](references/routing-policy.md)。模型目录超过刷新日期，或本机缓存的语义指纹（`etag`、可见模型清单、输入模态、支持/默认档位、升级与退役信息）发生变化时，先核验 OpenAI 官方文档和当前运行时；`fetched_at` 单独变化不构成目录过期。不能核验时标记 `needs-refresh`，不要凭旧表硬推。
3. 评估当前新对话或任务可预见的完整生命周期，而不是只看首轮轻量阶段。按调查、规划、执行、验证、部署和交付中预计出现的最高复杂度、上下文、工具负荷与风险下限填写路由字段；只有未知项会改变这一最高下限时才问一个关键问题。
4. 把分类结果传给 `scripts/route_model.py`。使用 `--json` 传 JSON 字符串或用 `--input` 传 JSON 文件；脚本输出仅是确定性基线，仍需核对真实任务语义和当前模型可用性。
5. 完整读取 [路由卡格式](references/routing-card-schema.md)，把机器结果转成一屏内的中文路由卡。明确标注推断、生命周期风险下限、相对额度、仅供明确重选时使用的升降档参考，以及运行时失效条件。
6. 展示唯一卡片后进入 `awaiting-user-confirmation`，请求用户在“按推荐执行 / 优先节省额度 / 优先保证质量”中确认。未确认时只继续等待或解释原卡，不重新计算和展示第二张。用户明确选择后进入 `routing-confirmed`，该选择覆盖本 Codex 对话或任务的完整生命周期；Skill 不会自动切换当前模型，只有运行时证据才能证明实际配置。
7. 若 V0.1 真实任务试运行处于激活状态，按“试运行记录”一节写入已确认的路由决策；不要在用户明确选择前记为接受。
8. 确认后静默沿用，不因阶段、目标细化、动作范围、风险、上下文、交付对象、材料更新、部署或归档恢复自动重路由。只有用户明确要求重选、明确改变额度偏好，或当前运行时证实所选模型不可用或已退役时，才把原选择标为 `routing-stale` 并显示一张替代卡。实质上另起新项目时，由新的 Codex 对话或任务入口生成新处方。

## 硬约束

- 先守住风险下限，再优化额度。不得因通用额度低而把生产、付款、公开发布、客户交付、隐私、安全或不可逆任务降到风险下限以下。
- 不承诺精确消耗或节省百分比。额度受上下文、输出、推理、工具、图片、缓存和计划影响，只给相对等级。
- 不把编译、测试或文件存在当作现实验收；模型升级不能替代真实数据、用户验收或外部完成证据。
- 不自动推荐 GPT-5.5。只有代表性 A/B 证据或已验证遗留兼容性明确支持时，才把它列为例外候选。
- 不把 `max` 当常规高档；它只用于最困难且难以拆分的单体问题。
- 不把 `ultra` 当普通“极高”；它只用于可以拆成独立部分的复杂任务，并会使用多 Agent。
- Spark 只用于当前目录确认可用的文本编码任务；涉及图片、公开交付、高风险动作或宽泛开放研究时不要选 Spark。
- 首次推荐必须覆盖当前对话可预见完整生命周期的最高风险与复杂度，不能因为开场只是调研或规划而低配。

## 与其他流程的边界

- 重大方向先完成项目调查、反方决策与用户方向确认，再做模型路由。
- 公开内容先服从内容门禁；被阻断时不进入写稿、制作或发布，无论推荐模型多强。
- 路由确认不等于高风险动作获批。生产变更、部署、公开发布、付款、删除、隐私处理、客户交付和外部消息仍须服从各自的授权、安全与验收门禁。
- 多 Agent 的角色和任务图由编排机制决定；本 Skill 只决定模型与推理档位。只有推荐 `ultra` 时才把“可真实并行”作为前提。

## 试运行记录

先检查 `/Users/pc/Documents/model-routing-advisor/evidence/trial-state.json`。仅当它存在且 `status` 为 `active` 时，完整读取 [试运行协议](references/trial-protocol.md)，并把事件追加到 `/Users/pc/Documents/model-routing-advisor/evidence/trial-events.jsonl`：

- 用户明确确认或改选路由卡后，用 `apply_patch` 追加一个 `route_decision`；完整复制送入路由器的原始字段和 `router_version`，不从推荐结果反推风险或评分。同一处方作用域内的阶段变化不生成第二张卡，也不得伪造新的用户确认；只有实际展示并确认替代卡时才追加新的路由决策。
- 任务完成、阻断、取消或停止时，用 `apply_patch` 追加一个 `task_outcome`。实际模型、档位、返工、耗时、评分或额度没有证据时写 `null`，不得猜测；填写返工或额度改善时，同时写入可定位的测试、验收、用户反馈或界面观测说明，否则不计效率信号。
- 录错时追加带 `supersedes_event_id` 的更正事件，不修改或删除历史行。
- 日志失败时明确标记 `trial-log-failed`；不要把该任务计入试运行证据，也不要声称试运行指标已更新。
- 每次追加后先运行 `scripts/summarize_trial.py`；校验通过后只暂存本次证据文件，确认相对上一个 Git 锚点只有尾部新增行，再提交和推送。不要用批量暂存把无关改动带入证据提交。

需要查看进度时，运行 `scripts/summarize_trial.py`。汇总结果只决定是否进入人工复核，不能自动启用全局门。
