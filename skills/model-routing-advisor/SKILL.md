# 模型路由顾问

为当前任务选择满足质量与风险下限的最小充分算力，并把推荐、理由、额度级别和升降档条件交给用户确认。

## 入口与触发

- 当本 Skill 被统一任务入口调用，或需要判断新路由、沿用、阶段变化、归档恢复及失败边界时，先完整读取 [全局门禁触发契约](references/global-gate-contract.md)，并在实质执行前给出其中定义的门禁状态。
- 门禁评估不等于每轮弹卡；`routing-not-required` 是同阶段安全沿用的有效结果，不能用沉默代替。
- 本 Skill 不能单独保证宿主在每个任务首轮调用它，也不能自动切换模型。V1 Hook 仅做 fail-open 注入与显式告警；高风险阻断仍是主执行者行为门，不是已验证的程序级工具硬锁。缺少宿主调用、确认凭证或运行时证据时，明确写“全局门未验证”或“实际模型未知”，不要夸大为绝对强制。

## 执行流程

1. 先确认上游门禁状态。若项目决策、内容生产、权限或安全门禁仍为阻断状态，返回 `blocked-upstream` 和阻断原因；不要用更强模型绕过门禁。
2. 每次生成新路由前，完整读取 [当前模型目录](references/current-model-catalog.md) 和 [路由策略](references/routing-policy.md)。模型目录超过刷新日期，或本机缓存的语义指纹（`etag`、可见模型清单、输入模态、支持/默认档位、升级与退役信息）发生变化时，先核验 OpenAI 官方文档和当前运行时；`fetched_at` 只是缓存刷新时间，单独变化不构成目录过期。不能核验时标记 `needs-refresh`，再按全局门禁契约的失败策略告警或阻断，不要凭旧表硬推。
3. 只评估本轮具体任务，不按项目名永久绑定模型。根据现有项目材料推断路由字段；只有未知项会改变风险下限时才问一个关键问题。
4. 把分类结果传给 `scripts/route_model.py`。使用 `--json` 传 JSON 字符串或用 `--input` 传 JSON 文件；脚本输出仅是确定性基线，仍需核对真实任务语义和当前模型可用性。
5. 完整读取 [路由卡格式](references/routing-card-schema.md)，把机器结果转成一屏内的中文路由卡。明确标注推断、风险下限、相对额度、升档条件和降档条件。
6. 展示卡片后进入 `awaiting-user-confirmation`，请求用户在“按推荐执行 / 优先节省额度 / 优先保证质量”中确认。用户明确选择后进入 `routing-confirmed`；入口若已实现并验证结构化持久化，再按全局门禁契约生成确认凭证，否则只能证明当前对话已确认，不能声称可跨归档自动恢复。Skill 不会自动切换当前任务的模型，只有运行时证据才能证明实际配置。
7. 若 V0.1 真实任务试运行处于激活状态，按“试运行记录”一节写入已确认的路由决策；不要在用户明确选择前记为接受。
8. 在同一阶段只沿用与当前任务指纹匹配的有效确认。阶段、独立目标、动作范围、风险、上下文规模、交付对象、用户偏好或路由基线显著变化时，把原凭证标为 `routing-stale` 并重新路由。

## 硬约束

- 先守住风险下限，再优化额度。不得因通用额度低而把生产、付款、公开发布、客户交付、隐私、安全或不可逆任务降到风险下限以下。
- 不承诺精确消耗或节省百分比。额度受上下文、输出、推理、工具、图片、缓存和计划影响，只给相对等级。
- 不把编译、测试或文件存在当作现实验收；模型升级不能替代真实数据、用户验收或外部完成证据。
- 不自动推荐 GPT-5.5。只有代表性 A/B 证据或已验证遗留兼容性明确支持时，才把它列为例外候选。
- 不把 `max` 当常规高档；它只用于最困难且难以拆分的单体问题。
- 不把 `ultra` 当普通“极高”；它只用于可以拆成独立部分的复杂任务，并会使用多 Agent。
- Spark 只用于当前目录确认可用的文本编码任务；涉及图片、公开交付、高风险动作或宽泛开放研究时不要选 Spark。

## 与其他流程的边界

- 重大方向先完成项目调查、反方决策与用户方向确认，再做模型路由。
- 公开内容先服从内容门禁；被阻断时不进入写稿、制作或发布，无论推荐模型多强。
- 多 Agent 的角色和任务图由编排机制决定；本 Skill 只决定模型与推理档位。只有推荐 `ultra` 时才把“可真实并行”作为前提。

## 试运行记录

先检查 `/Users/pc/Documents/model-routing-advisor/evidence/trial-state.json`。仅当它存在且 `status` 为 `active` 时，完整读取 [试运行协议](references/trial-protocol.md)，并把事件追加到 `/Users/pc/Documents/model-routing-advisor/evidence/trial-events.jsonl`：

- 用户明确确认或改选路由卡后，用 `apply_patch` 追加一个 `route_decision`；完整复制送入路由器的原始字段和 `router_version`，不从推荐结果反推风险或评分；同一阶段的一次真实任务及其结果沿用同一个 `task_id`，阶段变化需要重新路由时创建新的 `task_id`。
- 任务完成、阻断、取消或停止时，用 `apply_patch` 追加一个 `task_outcome`。实际模型、档位、返工、耗时、评分或额度没有证据时写 `null`，不得猜测；填写返工或额度改善时，同时写入可定位的测试、验收、用户反馈或界面观测说明，否则不计效率信号。
- 录错时追加带 `supersedes_event_id` 的更正事件，不修改或删除历史行。
- 日志失败时明确标记 `trial-log-failed`；不要把该任务计入试运行证据，也不要声称试运行指标已更新。
- 每次追加后先运行 `scripts/summarize_trial.py`；校验通过后只暂存本次证据文件，确认相对上一个 Git 锚点只有尾部新增行，再提交和推送。不要用批量暂存把无关改动带入证据提交。

需要查看进度时，运行 `scripts/summarize_trial.py`。汇总结果只决定是否进入人工复核，不能自动启用全局门。

## 维护与验证

维护本 Skill 时，使用 [离线评估夹具](references/evaluation-fixtures.json) 运行 `scripts/test_model_route.py` 与 `scripts/test_trial_summary.py`，再运行 Skill Creator 的 `quick_validate.py`。达到 7 天或至少 10 个真实任务后，用试运行协议的全部指标进行人工复核；在用户单独确认前不要接入全局强制门。
